# BiliBili-UWP 性能优化清单

> 日期：2026-11-01
> 依据：对当前仓库的静态审计 + 公开接口探测
> 说明：**“实测”** 指已核对代码/接口；**“推断”** 指基于代码结构的判断；**“待验证”** 指必须先运行才能确认。
> 前提：本机尚无 VS/SDK，应用未运行。所有收益数字都是目标，不是承诺；M0 能启动后先测基线，再逐项改。

---

## 0. 结论

优先级已调整为：**播放器性能与可用性 > 首页/请求层 > 工程现代化**。播放器是本项目的主路径，卡顿和崩溃的感知最强。

**本轮已完成（静态改动，未编译验证）**，详见第 2 节：

1. **弹幕渲染从“每 500ms 全量扫描”改为“有序列表 + 游标 + 二分重定位”。**
   原实现每个 tick 遍历整段弹幕并按时间窗过滤，弹幕量大时随长度线性变慢；现在每 tick 只处理新增窗口。
2. **移除起播关键路径上的弹幕/字幕加载，改为设置片源后后台异步加载。**
   原来必须先 `await LoadDanmaku()` + `await LoadSubtitle()` 才能设置 `MediaSource`。
3. **加入代次（generation）令牌，切分P/切番剧时丢弃过期结果。**
   原实现里旧分P的弹幕/字幕/片源请求可能在新分P之后返回并覆盖界面。
4. **重写播放器释放流程：解绑事件 → `Source = null` → `Dispose()`。**
   原来切P只新建 `MediaPlayer`，旧实例从未释放，事件也一直挂着。
5. **低价值高频回调降频/提前返回。**
   字幕计时器 10Hz → 4Hz；心跳只在播放中执行；普通视频不再响应互动 `PositionChanged`；封面按 960 宽解码。
6. **DASH 拉流改为共享 `HttpClient`**（`VideoService` / `AnimeService` 原来每次调用新建且从不释放）。

**尚未处理**：

- 弹幕解析本身仍由 `NSDanmaku` 库在调用线程上完成，只把排序放到了后台；是否阻塞 UI 需要在 M0 可运行后实测。
- 播放引擎 `SYEngine` 仍可能被启动时初始化（见 P0-4），属于启动路径而非播放路径。
- 所有收益数字都要等实机基线；当前不能声称“已变快”。

**下一批优先项**（按顺序）：

1. **增量加载人为延迟 1 秒 + UI 线程逐项添加**（P0-1，翻页体感最直接）。
2. **请求层共享 `HttpClient` + `ConfigureAwait(false)`**（P0-2，覆盖首页/详情页全部请求）。
3. **首页首屏并行化、事件订阅配对解除**（P0-3 / P0-5）。

## 2. 播放器 P0：本轮已实施（静态改动，未编译验证）

> 改动文件：`BiliBili-UWP/Components/Controls/VideoPlayer.xaml.cs`、`BiliBili-UWP/Models/UI/Others/VideoTransportControls.cs`、`BiliBili-Lib/Service/VideoService.cs`、`BiliBili-Lib/Service/AnimeService.cs`
> 状态：代码已写入，**本机无 .NET SDK / VS / Windows SDK，未编译、未运行**。以下“收益”均为结构性推断，不是实测数据。
> 回滚：改动集中在这 3 个文件，可按文件回退；没有改 XAML 结构，也没有引入新依赖。

### 2.1 弹幕：全量扫描 → 游标增量 + 二分重定位

**原实现（实测代码）**

`DefaultTimer_Tick` 每 500ms 遍历 `DanmakuList`，用时间窗过滤后再决定是否发射。弹幕列表越长，单 tick 成本越高；一次加载几千条时，每 0.5 秒都要扫一遍。

**现实现**

- 弹幕按 `time` 升序保存，新增游标 `_danmakuCursor` 和已发射位置 `_danmakuEmitPosition`（字段：`:122-127`）。
- 每个 tick 只向前推进到 `currentPosition + 1.0` 秒的窗口（`:1846-1883`），已处理的条目不再回看；`item.time <= currentPosition` 的条目直接跳过，保证拖动后不补放“过去”的弹幕。
- 用户拖动进度、倍速跳变时用二分查找重定位（`RebindDanmakuCursor`，`:834`）：找第一条 `time > position` 的弹幕。
- 只有“后退超过 1 秒”或“前进超过 4 秒”才重定位并清屏（`:1846`）；普通倍速播放不会频繁清屏。
- 每条弹幕仍受 `_maxDanmakuNumber` 单 tick 上限和屏蔽词过滤，逻辑不变。

**推断收益**

- 单 tick 成本从 O(弹幕总量) 降到 O(本 tick 新增条数)，长视频/大弹幕量下不再随时间变慢。
- 拖动进度后的重定位是 O(log n)，不再线性扫描。

**未做**

- 解析仍是 `NSDanmaku` 全量解析（`LoadDanmakuAsync`，`:774`），没有分段拉取。
- 只把排序移到了后台线程（`Task.Run`），解析调用本身没有包 `Task.Run`。

### 2.2 起播路径：侧数据不再阻塞片源设置

**原实现（实测代码）**

`RefreshVideoSource` 在创建 `MediaSource` 之前依次 `await LoadDanmaku()`、`await LoadSubtitle()`，弹幕接口慢时起播一起变慢。

**现实现**

- 两个重载（普通视频 `:495`、番剧 `:616`）都改为：先建片源 → 设置 `mediaElement.Source` → 再 `_ = LoadDanmakuAsync(); _ = LoadSubtitleAsync();`（`:591`、`:693`）。
- 弹幕/字幕失败只影响侧数据，不影响视频起播。

**推断收益**

- 起播时间不再叠加弹幕/字幕请求耗时。
- 弹幕接口异常时不会连带播放失败。

**代价**

- 起播后弹幕会晚一小段时间出现；如果解析很慢，仍可能占用线程（取决于库实现，待验证）。

### 2.3 代次令牌：切分P / 切番剧的竞态

**原实现（实测代码）**

切分P 时旧的异步请求没有失效机制。旧片源、旧弹幕、旧字幕如果在切换之后返回，会覆盖新分P的状态；旧片源甚至会和新分P的 `cid` 混用。

**现实现**

- 新增 `_sourceGeneration / _danmakuGeneration / _subtitleGeneration`（`:122-124`）。
- 每次 `RefreshVideoSource`、`LoadDanmakuAsync`、字幕加载开始时自增，`await` 之后逐次校验；不匹配直接丢弃（`:512`、`:559`、`:568`、`:628`、`:657`、`:666`、`:800`、`:806`、`:1051`、`:1062`）。
- 分P 变化时立即 `_playData = null`（`:500` 附近），避免拿旧片源给新分P建媒体源。
- 弹幕还用 `IsCurrentDanmakuPart(cid)` 二次确认 cid 未变。

**推断收益**

- 快速切P、切番剧、关闭播放器时不再出现“上一P的弹幕/片源回来覆盖当前P”。
- 旧请求的结果只浪费一次网络，不再污染 UI。

**未做**

- 没有取消底层 HTTP（`NSDanmaku` 未暴露 `CancellationToken`），只是丢弃结果。

### 2.4 播放器释放：解绑 + Dispose

**原实现（实测代码）**

切换分P/番剧时直接 `new MediaPlayer()`，旧实例既不 `Dispose()` 也不解绑事件；旧播放器的 `MediaOpened / MediaEnded` 回调仍会执行，并可能操作新播放器。

**现实现**

- 新增 `ReleasePlayer()`（`:1173`）：先解绑 `MediaEnded / MediaFailed / MediaOpened / VolumeChanged / PositionChanged / PlaybackStateChanged`，再 `Pause()` → `Source = null` → `Dispose()`，最后把 `_player` 置空（try/catch 包裹）。
- `Reset()`（`:242-263`）先 `mediaElement.SetMediaPlayer(null)`，再 `ReleasePlayer()`，然后才创建新实例。
- `Close()`（`:1144-1171`）停止两个定时器、作废所有代次、清空弹幕与缓存、解绑并释放播放器、销毁 `_tempSource`。
- 所有媒体事件都加了 sender 身份校验（例如 `sender != _player.PlaybackSession` 直接返回），旧实例的排队回调不会作用到新实例。

**依据**

- 微软文档：通过 `SetMediaPlayer` 设置的播放器由调用方负责关闭；释放顺序是先 `Source = null`，再解绑。
- 这是本轮唯一涉及资源生命周期的改动，属于“修可用性”而不只是性能。

### 2.5 高频回调降频 / 提前返回

| 项 | 原状 | 现状 | 位置 |
| --- | --- | --- | --- |
| 字幕计时器 | 100ms（10Hz） | 250ms（4Hz） | `:149` |
| 心跳 | 只要计时器在跑就发 | 仅 `PlaybackState == Playing` | `:1831` |
| 互动 `PositionChanged` | 普通视频也执行互动逻辑 | 无 `_videoDetail.interaction` 直接返回 | `:290` |
| 封面解码 | 按原图尺寸 | `DecodePixelWidth = 960` | `:178`、`:209` |
| 质量列表 | 追加不清空 | 每轮 `Clear()` 后重建 | 两个 `RefreshVideoSource` |
| 指针光标 | 每次移动都 `new CoreCursor` 并赋值 | 仅在 `PointerCursor == null` 时创建 | 指针移动处理 |
| 播放按钮状态回调 | `MediaPlayer` 为空时仍解引用 | 增加 `player != null` 判断 | `VideoTransportControls.cs` |
| 调试输出 | 手势处理里两处 `Debug.WriteLine` | 已删除 | — |

**推断收益**

- 字幕 10Hz → 4Hz，减少 UI 线程空转；字幕本身不是逐帧需求。
- 普通视频不再为互动逻辑做无用调度（`PositionChanged` 频率高，是热点回调）。

### 2.6 DASH 拉流共享 HttpClient

**原实现（实测代码）**

- `VideoService.cs`、`AnimeService.cs` 在 `CreateMediaSourceAsync` 内每次 `new HttpClient()`，使用后不释放。
- 注意：这里用的是 `Windows.Web.Http.HttpClient`（文件 `using Windows.Web.Http;`），不是 `System.Net.Http.HttpClient`。之前的文档把它写成 `System.Net.Http`，此处更正。

**现实现**

- 两个 Service 各增加一个 `static readonly` 共享实例 `_dashHttpClient`，固定 `Referer` 和 UA（`VideoService.cs:22-31`、`:258`；`AnimeService.cs:22-31`、`:173`）。
- 共享实例只用于拉取 MPD 文本，不承载登录 Cookie；带 Cookie 的 playurl 请求属于 M1/M2 的独立改动。

**推断收益**

- 复用连接，减少 MPD 拉取的握手开销；避免高频切P时累积未释放的 client。

**风险**

- `Windows.Web.Http.HttpClient` 的并发行为与 `System.Net.Http` 不同；固定 `DefaultRequestHeaders` 后没有按请求改头，暂未发现并发写头的问题，待运行验证。

### 2.7 顺带修掉的可用性问题

- 番剧 `mediaSource` 为 null 时，原代码会 `new MediaPlaybackItem(null)`；现在显示错误提示并返回（`:657` 附近）。
- `CurrentProgress` 在 `_player == null` 时返回 0，不再空引用。
- `SendDanmaku`、手势、历史续播、下一集等 UI 事件补了 `_player` 判空，`Close()` 之后不再崩。
- `HandleDashSource` 增加 `data.dash.audio != null` 判断，避免无音频流时索引空引用。

## 3. P0：优先修复（收益明确、风险可控）

### P0-1 增量加载人为延迟 1 秒 + UI 线程逐项添加

**证据（实测代码）**

`BiliBili-UWP/Models/UI/IncreaseCollection.cs`：

- 第 49-52 行：`_isBusy` 时直接 `throw`，增量加载异常可能冒泡到 ListView。
- 第 67-87 行：在 `dispatcher.RunAsync` 内调用 `_funcGetData(this)`，网络请求和后续处理都在 UI 线程上下文。
- 第 78 行：`foreach (var item in items) this.Add(item);`，每项一次 `CollectionChanged`。
- 第 88 行：`await Task.Delay(1000);`，每次加载固定多 1 秒。
- 第 91 行：`return new LoadMoreItemsResult { Count = (uint)this.Count };`，返回的是集合总数，不是本次加载的数量。

**影响**

- 每次触底翻页至少多等 1 秒（确定）。
- 一页 20～40 条会触发几十次 UI 通知，滚动/加载时掉帧（推断）。
- `LoadMoreItemsResult.Count` 语义错误，可能导致 ListView 对剩余项判断异常或重复请求（推断，需运行验证）。
- `_isBusy` 时抛异常而不是返回 0，快速滚动可能直接抛到 UI 线程（推断）。

**改法**

1. 删除 `Task.Delay(1000)`。
2. 把 `_funcGetData(this)` 移到 UI 线程之外执行（先 `await` 数据，再回 UI 批量添加）。
3. 用一次 dispatcher 调用批量添加；为避免 N 次通知，增加 `RangeObservableCollection.AddRange`，一次 `Reset` 通知（注意 ListView 滚动位置/选中项回归测试）。
4. 返回本次实际加入的数量：`Count = (uint)items.Count`。
5. 由数据源明确设置 `HasMoreItems`；忙时返回 `Count = 0` 而不是抛异常。
6. 删除第 89 行 `Debug.WriteLine(this.Count)`。

**验收**

- 翻页不再有固定 1 秒等待。
- 一页数据的 UI 通知次数从 N 次降到 1 次。
- 快速连续触底不抛异常、不重复加载同一页。
- 长列表滚动位置正常。

### P0-2 逐请求新建 HttpClient + JSON 在 UI 线程解析

**证据（实测代码）**

逐请求 `new HttpClient` 共 6 处：

- `BiliBili-Lib/Tools/BiliTool.cs:44`（`GetTextFromWebAsync`）
- `BiliBili-Lib/Tools/BiliTool.cs:117`（`GetStreamFromWebAsync`）
- `BiliBili-Lib/Tools/BiliTool.cs:145`（`PostContentToWebAsync`）
- `BiliBili-Lib/Tools/AppTool.cs:169`（`GetHtmlFromWeb`）
- `BiliBili-Lib/Service/VideoService.cs:258`（DASH MPD，**已改为共享实例，见第 2.6 节**）
- `BiliBili-Lib/Service/AnimeService.cs:173`（番剧 MPD，**已改为共享实例，见第 2.6 节**）

另有 `BiliTool.cs` 中 4 处 `HttpBaseProtocolFilter`（含 `GetCookies`、`ClearCookies`），全仓库共 11 处 client/filter 构造点。

解析位置：

- `BiliTool.cs:61`：`GetTextFromWebAsync` 在 `await client.GetAsync` 之后直接 `JObject.Parse(res)`，没有 `ConfigureAwait(false)`。
- `BiliTool.cs:100`：`ConvertEntityFromWebAsync` 在 await 后 `JsonConvert.DeserializeObject<T>`。
- 全仓库 `ConfigureAwait` 只有 `IncreaseCollection.cs:73` 一处。
- `Pages-Desktop` 下有 121 处 `await`（14 个文件），绝大多数由 UI 事件触发。

**影响**

- 每个请求新建连接池/过滤器，TLS 握手和连接复用差，请求延迟高（确定）。
- 高频请求可能造成端口/句柄压力（推断，需压测）。
- 当调用方在 UI 线程时，HTTP 完成后的 JSON 解析和对象构造都在 UI 线程，列表页/详情页容易卡顿（确定机制，实际卡顿程度待测）。
- `BiliTool.cs:42` 和 `:144` 忽略证书过期错误，属于安全问题（确定）。

**改法**

1. 在 `BiliTool` 内建立**单个** `HttpBaseProtocolFilter` + `HttpClient`（静态或 DI 单例），设置固定 UA/Referer/Accept。
2. 每个请求的差异头（Referer、Cookie、Content-Type）用 `HttpRequestMessage` 设置，避免并发修改 `DefaultRequestHeaders`。
3. `GetTextFromWebAsync` / `ConvertEntityFromWebAsync` / `PostContentToWebAsync` / `GetStreamFromWebAsync` 全部加 `ConfigureAwait(false)`；Lib 层不依赖 UI 上下文。
4. 重定向递归复用同一个 client，不重新创建。
5. 移除 `filter.IgnorableServerCertificateErrors.Add(ChainValidationResult.Expired)`。
6. `VideoService`/`AnimeService` 的 MPD 拉流也复用共享 client；注意它们用的是 `Windows.Web.Http.HttpClient`（不是 `System.Net.Http`），已按此实现，但**没有带 Cookie**——Cookie 要等 M1 的统一 `CookieManager` 方案。带 Cookie 的请求必须按 `HttpRequestMessage` 单独设置，不能改共享实例的默认头。
7. 共享 CookieManager 后，登录恢复时写入 Cookie；退出时清空。

**已完成部分**

- 第 6 项：两个 Service 已改为 `static readonly` 共享 `Windows.Web.Http.HttpClient`（第 2.6 节），但 Cookie 注入未做。
- 其余 1～5、7 项未做，`BiliTool` 仍是逐请求新建。

**验收**

- 同一页面的请求复用连接（请求日志/抓包可见 TLS 复用）。
- 请求完成后 JSON 解析不在 UI 线程（Debug 线程 ID 日志验证）。
- 移除证书忽略后，正常 HTTPS 请求不受影响。
- 首页/详情页滚动时无明显解析卡顿。

### P0-3 首页串行加载

**证据（实测代码）**

`BiliBili-UWP/Pages-Desktop/Main/HomePage.xaml.cs`：

- 第 63-70 行 `Refresh()`：先 `await channelVM.GetChannelSquareAsync()`，再 `await RefreshVideo()`。
- 第 114-124 行 `RefreshVideo()`：`while (i < 2)` 串行 `await LoadMoreRecommendVideo()`。
- 第 79 行：`data.ForEach(p => RecommendCollection.Add(p))`，逐项 UI 通知。
- 第 34 行：构造函数订阅 `IsLoginChanged`，登录状态变化会再次 `Refresh()`。
- 第 136-144 行：`Page_Loaded` 里 `await Task.Delay(100)` 后再恢复滚动位置。

**影响**

- 首屏至少 3 轮串行网络：频道广场 → 推荐第 1 页 → 推荐第 2 页（确定）。
- 第 2 页数据在首屏渲染前并不必需，却阻塞了完整加载（推断）。
- 登录状态变化可能触发一次完整刷新，和页面初始化刷新叠加（推断，需日志确认）。

**改法**

1. 频道广场与推荐第 1 页互不依赖，改为 `Task.WhenAll`。
2. 推荐第 2 页在首屏渲染后加载，或与第 1 页并行（第 2 页依赖第 1 页最后一条 `idx`，不能直接并行；可用首屏渲染完成事件触发）。
3. 批量添加推荐项（同 P0-1 的 AddRange）。
4. 给 `Refresh()` 加进行中标志，避免登录变化/页面加载/按钮重复触发。
5. `Task.Delay(100)` 改为在布局完成后恢复滚动（`LayoutUpdated` 一次或 `Dispatcher.RunAsync` 低优先级），不要固定等待。

**验收**

- 首屏请求从 3 轮串行降到 2 轮（频道+第 1 页并行，第 2 页后置）。
- 首屏内容出现时间下降（目标 -30%）。
- 登录状态变化不会导致重复刷新。
- 返回页面时滚动位置正常。

### P0-4 启动即初始化播放引擎、常驻定时器

**证据（实测代码）**

### P0-6 弹幕一次性全量解析

**证据（实测代码）**

- `Components/Controls/VideoPlayer.xaml.cs:692-708`：`LoadDanmaku()` 先 `DanmakuList.Clear()`，再 `await _danmakuParse.ParseBiliBili(cid)` 一次性解析整段弹幕。
- `:1333`：`_maxDanmakuNumber` 默认 200，只是显示上限。
- `NSDanmaku` 的解析和渲染在同一个库内；调用发生在 UI 上下文（推断）。

**影响**

- 弹幕量大时，进入播放页/切分P 会一次性解析整段，造成 UI 卡顿和内存峰值（推断，需用大弹幕量视频验证）。
- 只显示 200 条，却解析全部，存在浪费（确定设计）。
- 切换分P/关闭再打开会重复解析（推断）。

**改法**

1. 解析放到后台线程（`Task.Run` 或库本身的异步），完成后回 UI 赋值。
2. 解析后先按显示上限和屏蔽词过滤，再交给渲染层，避免把全量数据压进 UI 集合。
3. 切换分P/关闭弹幕时取消上一次加载（CancellationToken + 版本号，避免旧结果覆盖新分P）。
4. 评估分段加载（按时间片请求弹幕段），而不是一次性全量；这取决于现有弹幕接口和 NSDanmaku 能力。
5. 缓存同一 cid 的解析结果，避免重复解析。

**验收**

- 大弹幕量视频进入播放页无明显 UI 阻塞（<200ms）。
- 切分P 不出现旧弹幕闪回。
- 内存峰值下降（目标 -30%）。

**已完成部分（详见第 2.1 / 2.3 节）**

- 第 3 项：已用 `_danmakuGeneration` + `IsCurrentDanmakuPart(cid)` 实现，没有 `CancellationToken`（库不支持），旧结果直接丢弃。
- 第 5 项：已加 `_danmakuCache`（最多 3 个 cid），`Close()` 时清空。
- 排序已放到后台线程。
- 渲染侧已不再每个 tick 全量扫描，改为游标增量（第 2.1 节）。

**仍未做**

- 第 1 项：`ParseBiliBili` 调用本身没有包 `Task.Run`，需要先确认该库解析是否线程安全、是否依赖 UI 上下文。
- 第 2 项：全量解析结果仍在内存里，只是发射阶段才做上限/屏蔽过滤。
- 第 4 项：没有分段拉取。

## 4. P1：第二梯队（收益中等，改造面稍大）

### P1-1 图片解码尺寸审计

**证据（实测统计）**

- `DecodePixelWidth` 共 52 处，分布在 27 个文件；`BiliImage.xaml.cs` 有 8 处。
- 仍可能存在未设置解码宽度的路径：头像、横幅、动态图、代码创建的 `BitmapImage`（如 `AccountService.GetCaptchaAsync`）。

**问题**

- 未设置 `DecodePixelWidth` 的封面会按原图解码，内存占用高，长列表滚动容易抖动（推断）。
- 只设宽度不设 `DecodePixelType` 时，默认物理像素，在不同 DPI 下可能过大/过小。

**改法**

- 统一在 `BiliImage` / 模板中设置 `DecodePixelWidth`（按卡片实际显示宽度 × 缩放）和 `DecodePixelType="Logical"`。
- 头像等固定小图设置更小的解码宽度。
- 列表回收时取消未完成的图片加载（如果控件支持）。
- 审计 `HN.Controls.ImageEx` 是否支持解码宽度；不支持则换标准 `Image` 或 Toolkit `ImageEx`。

**验收**

- 长列表滚动内存峰值下降。
- 封面清晰度无明显下降。
- 快速滚动不因图片解码卡顿。

### P1-2 减少重复磁盘写入

**证据（实测代码）**

- `BiliViewModel.Main.cs:65-78`：每次 `GetRegionsAsync()` 成功都把 `region.json` 重写一遍（第 71 行），即使内容没变。
- `BiliViewModel.Main.cs:130-153`：emoji 在初始化/强制刷新时写 `emoji.json`。
- `AppTool.cs:19-45`：每次读写设置都 `CreateContainer`；`GetLocalSetting` 在键不存在时会**写入默认值**（第 42 行）。

**影响**

- 首页每次刷新都写磁盘；启动时读取大量设置可能触发多次容器创建/默认值写入（推断）。
- 不必要的 IO 会增加启动和刷新耗时，缩短闪存寿命（轻量）。

**改法**

- `region.json`/`emoji.json` 加 TTL 或内容哈希，内容不变不写；写入用临时文件 + 替换，避免半写。
- 缓存 `ApplicationDataContainer` 为静态字段，不在每次读写时 `CreateContainer`。
- `GetLocalSetting` 不写默认值；默认值只在设置页保存时写入。
- 写入合并/防抖（例如 500ms），避免连续设置变化触发多次写。

**验收**

- 首页连续刷新 10 次，`region.json` 只写 1 次（或内容变化时写）。
- 启动阶段设置写入次数为 0（首次运行除外）。

### P1-3 自动登录与消息轮询的请求次数

**证据（实测代码）**

- `BiliViewModel.Account.cs:116-139`：`AutoLoginAsync` 先 `CheckTokenStatusAsync()`，再 `GetMeAsync()`，成功路径至少 2 次网络请求。
- `MessageTimer_Tick` 每 10 分钟 `CheckUnreadMessage()` + `SSO()`。

**改法**

- 直接用 `GetMeAsync()` 判断登录态；失败（-101/未登录）再刷新 token。成功时省掉一次 `checkToken` 请求。

- 消息轮询只在已登录且应用可见时进行；失败指数退避。

**验收**

- 启动自动登录成功路径从 2 次请求降到 1 次。
- 未登录/后台时不发消息轮询。

### P1-4 日志脱敏与降噪

**证据（实测代码）**

**验收**

- 正常使用时日志量明显下降。

## 5. P2：可选/长期

### P2-1 Native AOT

- 现代 UWP 支持 `PublishAot`，但要求所有代码 AOT 兼容；本项目有 Newtonsoft 反射、XAML `{Binding}` 类、第三方 UWP 库，改造成本高。
- 若要做：
  - 先把 JSON 换成 `System.Text.Json` 源生成；
  - 给 XAML 绑定的类加 `[GeneratedBindableCustomProperty]` 并设为 `partial`；
  - 给 Lib/Controls 设 `IsAotCompatible`，逐项消除 AOT/裁剪警告；
  - 第三方库逐个确认 AOT 支持，不支持就替换。
- 结论：**本轮不做**；JIT 版本先满足个人使用。AOT 的启动收益官方基准约 5%，不值得在功能未稳定时投入。

### P2-2 绑定与虚拟化审计

- 现有 `HomePage.RecommendVideoView_ContainerContentChanging` 已使用 `args.Handled = true`（好模式）；其他长列表可复用。
- `AdaptiveGridView` 使用 `ItemsWrapGrid`，默认是虚拟化的；不要为了“优化”改成普通 `StackPanel`。
- 是否需要把热点模板的 `{Binding}` 改成 `x:Bind`，要先测量；盲目改会引入大量编译错误。
- 只审计长列表（首页推荐、搜索结果、收藏、历史、评论），不要全量重写。

### P2-3 WinUI 3 / Windows App SDK

- 属于长期路线，不是本轮性能优化。现代 .NET UWP 已经能拿到大部分运行时收益；WinUI 3 迁移会带来 UI 重写成本。
- 如果未来要做，按官方建议：先完成 .NET 迁移和功能稳定，再单独迁移 UI 框架。

## 7. 不建议做的事

- **不要在依赖兼容性未验证前开 `PublishAot`**：会先卡在第三方库和反射，耽误主线。
- **不要把所有请求无脑并行**：B 站有风控，首页/搜索突发并发容易触发 `-352/-412`；只并行互不依赖且数量可控的请求。
- **不要把 `ObservableCollection` 换成 `List`**：会失去增量加载和 UI 通知，列表不会更新。
- **不要为了帧率盲目关闭动画**：现有动画不是主要瓶颈，先解决 1 秒延迟和 UI 线程解析。
- **不要在日志里保留完整 URL**：`access_key`/`SESSDATA` 泄露比性能问题更严重。
- **不要在没有基线的情况下改 XAML 模板**：模板改动面大，收益不明确，容易引入回归。
