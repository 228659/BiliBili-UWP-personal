# BiliBili-UWP 修复与现代化方案

> 项目：Richasy/BiliBili-UWP（GPL-3.0，已归档）
> 日期：2026-11-01
> 使用范围：个人使用，Windows 11 x64，仅扫码登录
> 结论标注：**实测** = 已核对代码或发起过公开请求；**推断** = 基于代码结构的判断；**待验证** = 需要编译或实机运行确认

---

## 0. 一页结论

1. **不能用的原因不是单点**：密码登录接口已失效、部分旧 API 下线、构建/签名/分发链也失效。
2. **不重写 UI**。采用路线 A：保留现有 UWP XAML 结构，原地升级到现代 .NET UWP（`net10.0-windows10.0.26100.0`），只保留 x64。
3. **优先级已按“先能用、再流畅”调整**：播放器性能与可用性（已改代码，未编译验证）→ M0 可构建可启动 → M1 仅 TV 扫码登录 → M2 核心 API → M3 其余性能与收尾。
4. **播放器侧静态瓶颈已处理**（详见 [`性能优化.md`](性能优化.md) 第 2 节）：
   - 弹幕渲染从每 500ms 全量扫描改为有序列表 + 游标 + 二分重定位；
   - 起播不再等待弹幕/字幕加载；
   - 切分P 加入代次令牌，旧请求结果不再覆盖新分P；
   - `MediaPlayer` 改为解绑 + `Dispose()`，修复切换时实例泄漏与旧回调串台；
   - 字幕计时器 10Hz → 4Hz、心跳仅播放中、普通视频跳过互动位置回调、封面 960 宽解码；
   - `VideoService` / `AnimeService` 的 DASH 拉流改为共享 `HttpClient`。
   - **注意：以上只做了代码修改，本机没有工具链，全部未编译、未实机验证。**
5. **其余性能瓶颈已定位**（静态审计）：
   - 增量加载每次人为 `Task.Delay(1000)`；
   - `BiliTool` 仍逐请求新建 `HttpClient`，JSON 解析回到 UI 线程；
   - 首页频道、推荐第 1 页、推荐第 2 页串行请求；
   - 启动即初始化播放引擎、常驻定时器、页面事件未解除订阅。
6. **本机当前没有编译工具链**（实测）：只有 .NET 10 运行时，没有 .NET SDK、Visual Studio、Windows SDK。代码可以先改，但第一次编译、打包、运行需要先安装 **VS 2026 + UWP 工具 + Windows SDK 10.0.26100**。安装完成前，本文中的“编译通过/运行通过”都只能算待验证。
7. **最大技术风险**：`SYEngine`、`NSDanmaku`、`HN.Controls.ImageEx.Uwp`、`Richasy.Font.UWP` 这些 UWP-only 依赖能否在现代 .NET UWP 下还原并运行。M0 第一次 `restore` 就会暴露；如果不行，按第 6.3 节的备选方案替换，M2 工期可能增加 3～5 个工作日。

### 1.3 接口探测结果（实测，2026-11-01，全部为无凭据公开请求）

| 探测项 | 结果 | 结论 |
| --- | --- | --- |
| 旧 appkey + sign 的匿名接口 | 多数返回 200 | 旧签名机制本身仍可用，不是“API 全死” |
| `POST https://passport.bilibili.com/api/v3/oauth2/login` | 405 | 账号密码登录已失效，必须改扫码 |
| 频道 `square2` / `detail` | 404 | 相关页面需要换接口或降级 |
| 匿名 `playurl` | 返回 flv 720P，不含 DASH | 高清/DASH 需要登录 Cookie |
| TV 扫码 `qrcode/auth_code` | 200，`code=0`，返回 `url` + `auth_code` | TV 扫码可用 |
| TV 扫码 `qrcode/poll`（未扫码） | 200，`code=86039`“二维码尚未确认” | TV 轮询可用，但不区分“未扫码”和“已扫码未确认” |
| Web 扫码 `generate` | 200，返回 `qrcode_key` + H5 登录 URL | Web 扫码可用 |
| Web 扫码 `poll`（未扫码） | 根 `code=0`，`data.code=86101` | 需要判断 `data.code`，不能只看根 `code` |

> 探测使用的 TV appkey：`4409e2ce8ffd12b8`，secret：`59b43e04ad6965f34319062b478f83dd`。这是公开的 TV 端密钥，不是用户凭据。
>
> 没有完成真实扫码，因此“扫码成功后返回的 token/cookie 字段”来自接口文档，标记为待验证。

### 1.4 登录现状（实测，来自代码）

- `Components/Account/LoginPopup.xaml` 有用户名、密码、验证码输入框，以及“网页扫码登录”按钮。
- `LoginPopup.xaml.cs` 调用 `Account.LoginAsync(userName, password, captcha)`；该接口就是已返回 405 的 `/api/v3/oauth2/login`。
- “网页扫码登录”打开 `https://passport.bilibili.com/ajax/miniLogin/minilogin`，再解析 `access_key`。这条链路属于旧网页登录，和密码登录一起失效，不能作为新方案。
- 登录成功后只保存 `AccessToken / RefreshToken / TokenExpiry`（`Settings` 枚举），**没有保存 Cookie**。
- `BiliTool` 通过 `access_key` 调用 App 接口；`GetTextFromWebAsync` 不注入 Cookie，因此后续 WBI 接口无法直接复用登录态。
- `BiliTool.cs:42` 忽略了证书过期错误（`ChainValidationResult.Expired`），属于安全问题，需要移除。

## 2. 目标与非目标

### 目标

- 在 Windows 11 x64 上能编译、打包、侧载安装、启动。
- 登录只保留扫码：TV 二维码为主，Web 二维码为兜底；删除账号密码和验证码。
- 恢复核心使用路径：首页推荐、视频详情、播放、番剧、搜索、收藏、历史、稍后再看。
- 首页首屏、翻页、滚动明显变顺；不追求极限性能，先消除人为延迟和明显的 UI 线程阻塞。
- 保持现有视觉风格和页面结构，不做大改版。

### 非目标

- 不上架微软商店。
- 不做 ARM64（SYEngine 没有 arm64 原生库）。
- 不做多账号、账号密码登录、短信登录。
- 不在本轮迁移到 WinUI 3 / Windows App SDK。
- 不保证所有旧接口都恢复；动态、评论、直播等模块按 M2 的优先级逐个验证。
- 不默认开启 Native AOT；先保证 JIT 版本可运行。

## 3. 路线选择

| 路线 | 内容 | 成本 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A | 原地现代化 UWP：保留 XAML/页面结构，升级现代 .NET | 中 | 旧 UWP 依赖兼容性 | **采用** |
| B | 迁移 WinUI 3 / Windows App SDK | 高 | 106 个左右 XAML 视图、导航、播放器全部重写 | 不做 |
| C | 基于 Bili.Copilot / bili-kernel 另起项目 | 中高 | 功能恢复不等于原项目恢复，UI 需重做 | 不作为主线 |
| D | 只修 API，保留 .NET Native 旧栈 | 低 | 构建链仍是旧模型，换机/升级困难 | 只作为回滚兜底 |

选择 A 的原因：

- 现有页面、控件、主题、播放器逻辑可以继续用，恢复成本最低。
- 微软已把现代 .NET UWP 作为 VS 2026 的默认 C# UWP 项目类型，官方支持 `.NET 10 + Native AOT`，后续仍有升级路径。
- 官方给出的增量路径就是“先升级 .NET，再考虑 WinUI 3”；不需要一次做完。

## 4. 目标技术栈

| 项 | 目标 | 说明 |
| --- | --- | --- |
| IDE | Visual Studio 2026（Community 即可） | 需勾选“通用 Windows 平台工具”和 Windows 11 SDK 10.0.26100 |
| 目标框架 | `net10.0-windows10.0.26100.0` | 官方现代 UWP 模板值 |
| 最低版本 | `10.0.19041.0` | Windows 10 2004+；Win11 满足 |
| 项目格式 | SDK 风格 csproj | `UseUwp`、`EnableMsixTooling` |
| 输出类型 | `WinExe` | 现代 UWP 应用 |
| 架构 | 仅 x64 | 移除 x86/ARM/ARM64 配置 |
| UI 库 | Microsoft.UI.Xaml 2.8.7 | WinUI 2 最后稳定版 |
| Toolkit | Microsoft.Toolkit.Uwp.* 7.1.3 | 6.x → 7.x 有 API 变化，需逐项编译修正 |
| 2D | Win2D.uwp 1.28.3 | 现有 1.25.0 升级 |
| JSON | Newtonsoft.Json 13.0.4 | 先保留，减少改动；AOT 阶段再评估 System.Text.Json |
| 二维码 | QRCoder 1.8.1（`PngByteQRCode`） | 不依赖 System.Drawing，输出 PNG 字节 |
| 响应式 | System.Reactive 7.0.0 | 仅 2 处使用；如果升级冲突，可先移除依赖并改写 |
| AOT | 暂不开启 `PublishAot` | 需要 AOT 兼容改造，放到 M3 评估 |
| 自包含 | `SelfContained=true` | 现代 .NET UWP 要求 `PublishAot` 或 `SelfContained` 二选一；JIT 路线选后者 |
| 签名 | 自签名证书 | 不再使用作者证书；发布者名与证书 Subject 一致 |
| 打包 | 单项目 MSIX，x64 | 不再生成 arm64 bundle，不写死 D 盘 |

> 不默认开 `PublishAot` 的原因：官方文档明确要求所有代码 AOT 兼容；本项目大量使用 Newtonsoft 反射和 XAML `{Binding}`，第三方 UWP 库也未必支持。先跑通 JIT，性能收益优先从 [`性能优化.md`](性能优化.md) 的 P0 项拿。
>
> `SelfContained=true` 不是可选项：现代 .NET UWP 在没有 `PublishAot` 时必须自包含运行时，否则不会生成可部署的包。它会让输出体积变大，但个人使用可以接受。后续如果要减小体积，再评估 AOT/裁剪，不要一开始就开。

## 6. M0：工程现代化（先做到能构建）

### 6.1 目标

- 解决方案能在 VS 2026 下还原、编译 x64 Debug/Release。
- 生成可侧载的 MSIX 包，安装后能启动到欢迎页/主页面。
- 先不追求所有 API 可用；匿名首页能显示、页面能导航即可。

### 6.2 文件级改动

#### `BiliBili-UWP/BiliBili-UWP.csproj`

- 改为 `<Project Sdk="Microsoft.NET.Sdk">`。
- 关键属性：

```xml
<OutputType>WinExe</OutputType>
<TargetFramework>net10.0-windows10.0.26100.0</TargetFramework>
<TargetPlatformMinVersion>10.0.19041.0</TargetPlatformMinVersion>
<UseUwp>true</UseUwp>
<EnableMsixTooling>true</EnableMsixTooling>
<Platforms>x64</Platforms>
<PlatformTarget>x64</PlatformTarget>
<RootNamespace>BiliBili_UWP</RootNamespace>
<AssemblyName>BiliBili-UWP</AssemblyName>
<DefaultLanguage>zh-CN</DefaultLanguage>
<SelfContained>true</SelfContained>
<RuntimeIdentifier>win-x64</RuntimeIdentifier>
```

> `SelfContained` 和 `RuntimeIdentifier` 是 JIT 路线能产出可部署包的前提；如果后续改用 `PublishAot=true`，则不再需要 `SelfContained`。

- 删除：`AppContainerExe`、`UseDotNetNativeToolchain`、`TargetPlatformIdentifier=UAP`、全部旧 `Debug|ARM/ARM64/x86` 配置、`AppxBundlePlatforms=arm64`、`AppxPackageDir>D:\...`、作者证书指纹、`MinimumVisualStudioVersion=14`、旧 `Microsoft.Windows.UI.Xaml.CSharp.targets` 导入。
- 显式 `Compile/Page/Content` 列表交给 SDK 通配符；只保留必要的 `None/Content` 特殊项。
- 保留 `Package.appxmanifest` 作为 `AppxManifest`。
- `AppxBundle` 先设为 `Never`；`AppxPackageDir` 改到解决方案下的 `AppPackages\`。
- 包引用升级：WinUI 2.8.7、Toolkit 7.1.3、Win2D 1.28.3、Newtonsoft 13.0.4、QRCoder 1.8.1。
- `Microsoft.NETCore.UniversalWindowsPlatform` 移除（现代 .NET UWP 不再需要）。
- 项目引用保留 Lib/Controls；**Notification 在 M0 暂时移除引用**（见 6.3）。

#### `BiliBili-Lib/BiliBili-Lib.csproj`

- SDK 风格类库：`TargetFramework` 同上，`UseUwp>true`，`OutputType>Library`。
- 移除 UWP 6.2.9 包；Newtonsoft 升到 13.0.4。
- 保留 `MetroLog`、`QueryString.NET`；如果还原失败，按 6.3 替换。
- 移除 `BiliBili_Lib.rd.xml` 的 EmbeddedResource（现代 .NET 不使用运行时指令；AOT 阶段再用注解/分析器）。

#### `BiliBili-Controls/BiliBili-Controls.csproj`

- SDK 风格 XAML 类库：`TargetFramework` 同上，`UseUwp>true`。
- `Bubble\Bubble.xaml` 交给 SDK 的 XAML 项；Win2D 升到 1.28.3。
- 移除 UWP 6.2.9 包和 `rd.xml`。

#### `BiliBili-Notification/BiliBili-Notification.csproj`

- 这是一个 `winmdobj` 输出、给后台任务用的 WinRT 组件，**M0 先移出解决方案和主项目引用**，同时从 `Package.appxmanifest` 移除 `NewDynamicNotification` 的后台任务扩展。
- 原因：现代 .NET UWP 的 WinRT 组件模板与旧 `winmdobj` 不同，先让主应用能构建；后台动态通知在 M3 用现代模板重新接回，或按个人使用需求直接不做。
- 现有设置页的按需注册逻辑（`AppViewModel.RegisterBackgroundTask`）保留，但 M0 不注册该任务。

#### `BiliBili-UWP/Package.appxmanifest`

- `TargetDeviceFamily`：`MinVersion="10.0.19041.0"`，`MaxVersionTested="10.0.26100.0"`。
- Identity `Publisher` 改成自签名证书的 Subject，例如 `CN=BiliBiliUWP-Personal`。
- 移除 `NewDynamicNotification` 的 `windows.backgroundTasks` 扩展（M3 再接）。
- 保留协议 `richasy-bilibili`、`startupTask`；确认 `Executable`/`EntryPoint` 与现代 .NET UWP 模板一致。
- 只保留 x64 架构。

#### 解决方案与杂项

- `BiliBili-UWP.sln`：删除 ARM/ARM64/x86 配置，只保留 x64；移除 Notification 项目（M0）。
- 删除 `Package.StoreAssociation.xml`（作者商店关联，已无意义）。
- 删除 `Properties/Default.rd.xml` 引用（文件可保留但不是构建项）。
- `.gitignore` 增加自签名证书、`AppPackages/`、本地打包密码文件。

### 6.3 依赖兼容性：先验顺序与备选

M0 第一次 `restore/build` 按下面顺序验证，遇到问题按备选处理：

| 依赖 | 用途 | 风险 | 备选 |
| --- | --- | --- | --- |
| `SYEngine.uwp 1.0.7` | DASH/FLV 播放引擎 | **最高**。老 UWP 原生组件，无 arm64；现代 .NET UWP 能否加载待验证 | 先原样引用；失败则改用 `MediaPlayerElement + AdaptiveMediaSource`（DASH）或保留旧 .NET Native 分支；工期 +3～5 天 |
| `NSDanmaku 1.5.1` | 弹幕解析与渲染 | 高。老 UWP XAML 库 | 先原样；失败则把解析改为自研（B 站弹幕 XML 简单），渲染用 Canvas/Composition 或第三方替代 |
| `HN.Controls.ImageEx.Uwp 1.0.29` | XAML 图片控件 | 中。使用面广（30 个文件） | 换成 `Microsoft.Toolkit.Uwp.UI.Controls.ImageEx` 或标准 `Image` + 解码宽度；需逐个模板改 |
| `Richasy.Font.UWP 1.0.5` | 图标字体资源 | 低 | 项目已带 `Assets\Fonts\Richasy_BiliBili.ttf`，可直接 `FontFamily` 引用 |
| `Microsoft.Toolkit.Uwp.* 6.x` | 控件/动画/通知/连接 | 中。6→7 有 API 变化 | 升级到 7.1.3 后按编译错误逐项修；必要时移除未使用包 |
| `MetroLog 1.0.1` | 日志 | 低 | 换成简单 `Debug.WriteLine`/文件日志 |
| `Win2D.uwp 1.25.0` | 2D 绘制 | 低 | 升 1.28.3；若 API 差异按编译错误修 |

## 7. M1：仅扫码登录（删除密码）

### 7.1 交互目标

登录弹窗只保留二维码，不再出现用户名、密码、验证码、WebView 迷你登录。

状态：

1. 正在生成二维码
2. 请使用哔哩哔哩手机客户端扫码
3. 等待手机确认（TV 轮询不区分“已扫码”，只能统一提示“扫码后在手机上确认”）
4. 登录成功
5. 二维码已过期，点击刷新
6. 网络错误/接口风控，提示重试

交互细节：

- 弹窗打开立即生成，不等用户点按钮。
- 二维码有效期 180 秒；轮询间隔 2 秒；关闭弹窗立即取消轮询。
- 过期后显示“刷新二维码”按钮，不自动无限重试。
- 登录成功后关闭弹窗，刷新头像/昵称/侧栏登录态。
- 不自动弹出登录框；需要登录的操作仍走现有 `ShowLoginPopup()`。

### 7.2 协议（实测 + 文档字段）

#### TV 扫码（主方案）

**生成二维码**

```
POST https://passport.bilibili.com/x/passport-tv-login/qrcode/auth_code
Content-Type: application/x-www-form-urlencoded
User-Agent: Mozilla/5.0 BiliDroid/... (TV/Android UA)

appkey=4409e2ce8ffd12b8
local_id=0
ts=<unix 秒>
sign=<按 key 排序后拼接 + secret 的 MD5 小写>
```

实测响应（2026-11-01）：

```json
{
  "code": 0,
  "message": "OK",
  "ttl": 1,
  "data": {
    "url": "https://passport.bilibili.com/x/passport-tv-login/h5/qrcode/auth?auth_code=...",
    "auth_code": "..."
  }
}
```

用 `data.url` 生成二维码，保存 `data.auth_code`。

**轮询**

```
POST https://passport.bilibili.com/x/passport-tv-login/qrcode/poll
Content-Type: application/x-www-form-urlencoded

appkey=4409e2ce8ffd12b8
auth_code=<上一步>
local_id=0
ts=<unix 秒>
sign=<同上>
```

实测未扫码：`code=86039`，`message="二维码尚未确认"`。
已知状态：`0` 成功、`86039` 未确认、`86038` 已失效、`-3` 签名错误、`-400` 请求错误。

成功时（按接口文档，待实机扫码验证）`data` 包含：

- `access_token`、`refresh_token`、`expires_in`
- `cookie_info.cookies[]`：至少 `SESSDATA`、`bili_jct`、`DedeUserID`、`DedeUserID__ckMd5`，可能带 `sid`

> TV 轮询不区分“未扫码”和“已扫码未确认”，所以 UI 不要伪造“已扫码”状态；统一提示“扫码后在手机上确认”。

#### Web 扫码（兜底，不保证全部 App 接口）

```
GET https://passport.bilibili.com/x/passport-login/web/qrcode/generate
→ data.url, data.qrcode_key

GET https://passport.bilibili.com/x/passport-login/web/qrcode/poll?qrcode_key=...&source=main-fe-header
→ 根 code=0，判断 data.code：
   86101 未扫码
   86090 已扫码未确认
   86038 已失效
   0     成功
```

实测未扫码：根 `code=0`，`data.code=86101`。成功时 `data.url` 的查询串和 `Set-Cookie` 带 `SESSDATA / bili_jct / DedeUserID / DedeUserID__ckMd5`，以及 `refresh_token`。

限制：Web 扫码通常**没有 `access_key`**。现有大量接口使用 `hasAccessKey: true`，因此 Web 扫码只作为 TV 扫码失败时的兜底，不承诺账号相关接口全可用。

### 7.3 登录状态机

```
打开弹窗
  → Generating（POST auth_code）
  → Waiting（显示二维码，每 2s poll）
      ├─ 86039 → 继续 Waiting
      ├─ 86038 → Expired（显示刷新按钮）
      ├─ 0     → 保存 token + cookies → GetMe → Success → 关闭
      └─ 网络错误 → 提示重试，不无限循环
关闭弹窗 → 取消 poll（CancellationToken）
```

### 7.4 数据模型与存储

新增模型（建议放在 `BiliBili-Lib/Models/BiliBili/Login.cs` 或单独 `QrLoginModels.cs`）：

```csharp
public sealed class QrLoginSession
{
    public string Url { get; set; }
    public string AuthCode { get; set; }
    public string QrCodeKey { get; set; }
    public DateTimeOffset ExpiresAt { get; set; }
}

public sealed class QrLoginResult
{
    public string AccessToken { get; set; }
    public string RefreshToken { get; set; }
    public int ExpiresIn { get; set; }
    public Dictionary<string, string> Cookies { get; set; }
    public long UserId { get; set; }
}
```

存储：

- 复用 `Settings` 枚举的 `AccessToken / RefreshToken / TokenExpiry / UserId`。
- 新增 `SESSDATA / BiliJct / DedeUserId / DedeUserCkMd5`（追加到枚举末尾，保持旧键兼容）。
- 写入 `ApplicationData.Current.LocalSettings` 的 `BiliBili` 容器；个人使用可接受应用沙箱明文。可选增强：用 `DataProtectionProvider` 做本地加密。
- 不把 token、cookie、`access_key` 写进日志；日志里的 URL 需要脱敏。

Cookie 注入：

- `BiliTool` 改为共享一个 `HttpBaseProtocolFilter` + `HttpClient`；启动恢复登录时把持久化的 Cookie 写入共享 `CookieManager`。
- Cookie 域使用 `.bilibili.com`，路径 `/`。

- 退出登录时清空 CookieManager 和本地 Cookie 设置。

### 7.6 自动登录顺序

1. 读取 `AccessToken / RefreshToken / TokenExpiry` 和 Cookie。
2. 若 Cookie/Token 存在且 `TokenExpiry` 未临近（留 5 分钟余量）→ 直接 `GetMe`。
3. `GetMe` 失败（-101/未登录）→ 用 `RefreshTokenAsync` 刷新；成功则重试 `GetMe`。
4. 刷新失败 → 清空登录态，不弹错误框；用户点登录时再扫码。
5. 不再用 `SSO` 作为启动登录的必经步骤（扫码已经拿到 Cookie）。

## 8. M2：核心 API 修复

M2 的不确定性最高，按“能看能播”优先，逐个模块交付。

### 8.1 先做诊断能力

- 在 `BiliTool` 统一记录：URL（脱敏）、HTTP 状态、`code`、`message`、耗时。
- 失败时 UI 显示可读错误（登录失效、风控、接口下线、网络错误），不要只显示“加载失败”。
- 对 `-352`、`-412`、`-799` 等风控码做限速/退避，不无限重试。

### 8.2 WBI 与 Cookie

现代 Web 接口需要 WBI：

- `GET https://api.bilibili.com/x/web-interface/nav` 取 `wbi_img.img_url`、`wbi_img.sub_url`。
- 取文件名拼 `mixin key`，按固定 64 字符置换表生成。
- 请求参数按 key 排序，加 `wts`，拼接 mixin key 后 MD5 得到 `w_rid`。
- 配合 Cookie（`SESSDATA`、`buvid3`）使用。
- 需要时先请求 `https://api.bilibili.com/x/frontend/finger/spi` 获取 `buvid3/buvid4`。

WBI 只用于 Web 接口；现有 App 签名接口继续用旧 `appkey + sign`，不要混用密钥（否则可能 `-663`）。

### 8.3 播放

- 播放地址优先走 `https://api.bilibili.com/x/player/wbi/playurl`，带 `fnval=4048`、`fourk=1`、`qn`、Cookie、WBI 参数。
- 匿名只能拿到 flv 720P；1080P+/DASH 需要有效 Cookie（实测匿名 playurl 不含 DASH）。
- 现有 `VideoService.CreateMediaSourceAsync` 手工拼 MPD。需要核对：
  - MPD 中的视频/音频 SegmentBase 与 backup URL 是否完整；
  - `Referer`/UA/Cookie 是否带上；
  - SYEngine 是否支持该 MPD 写法。
- 若 SYEngine 在现代 .NET 下不可用，备选是 `MediaPlayerElement + AdaptiveMediaSource`；这属于 M0 6.3 的高风险项，不在 M2 默认范围。
- `qn` 与会员权益相关；没有会员账号时不要承诺 1080P+/4K。

### 8.4 模块优先级

| 优先级 | 模块 | 说明 |

| P0 | 首页推荐、视频详情、播放、分P | 最小可用闭环 |

```powershell
  )

$pwd = ConvertTo-SecureString -String "你的证书密码" -Force -AsPlainText
Export-PfxCertificate -Cert $cert -FilePath ".\BiliBili-UWP.pfx" -Password $pwd
Export-Certificate -Cert $cert -FilePath ".\BiliBili-UWP.cer"
Import-Certificate -FilePath ".\BiliBili-UWP.cer" -CertStoreLocation "Cert:\LocalMachine\TrustedPeople"
```

要点：

- `Package.appxmanifest` 的 `Publisher` 必须等于 `CN=BiliBiliUWP-Personal`。
- 在本地用用户级 `.user` 文件或环境变量提供 `PackageCertificatePassword`，不要把密码写进 csproj。
- `.pfx`、密码、`AppPackages/` 加入 `.gitignore`。
- 信任证书需要管理员权限（会弹 UAC）。

### 11.4 安装

- 开启 Windows 开发者模式/旁加载。
- 方式一：安装生成的 `.msix`：

```powershell
Add-AppxPackage -Path ".\AppPackages\BiliBili-UWP_..._x64.msix"
```

- 方式二：开发阶段注册松散文件：

```powershell
Add-AppxPackage -Register ".\BiliBili-UWP\bin\x64\Debug\AppxManifest.xml"
```

## 12. 风险与回滚

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 旧 UWP 依赖与现代 .NET 不兼容（SYEngine/NSDanmaku/ImageEx） | M0 无法构建或播放不可用 | M0 先 restore 验证；按 6.3 替换；最坏情况保留旧 .NET Native 分支作为回滚 |
| Toolkit 6→7 / WinUI 2.4→2.8 API 变化 | 编译错误多 | 按编译错误逐个修；先保功能，不做样式重构 |
| WinRT 后台任务组件不兼容 | 动态通知不可用 | M3 再处理，或删掉该功能（个人使用可接受） |
| 扫码接口风控/改版 | 登录失败 | TV + Web 双通道；加 UA/设备参数；失败提示重试，不无限轮询 |
| `refresh_token` 接口失效 | 启动自动登录失败 | 实测确认；失败则要求重新扫码，不阻塞应用启动 |
| 高清/DASH 需要会员 Cookie | 只能 720P/FLV | 这是账号权益，不是代码缺陷；不承诺未登录高清 |
| Native AOT 兼容性 | 构建失败/运行时崩溃 | 本轮不开 AOT；M3 单独评估 |
| 自签名证书/发布者不匹配 | 无法安装 | Publisher 与证书 Subject 保持一致；重新生成证书 |
| 工具链未安装 | 无法编译验证 | 你先安装 VS 2026 + UWP 工具 + SDK 26100 |

回滚策略：

- 新建分支 `modernize/m0`，原始提交打标签 `legacy-2021`；每个里程碑单独提交，出问题可按里程碑回退。
- 不直接删除原文件；先改构建配置，再改代码。M0 出问题时可回到旧 csproj。
- 本地设置键保持兼容，新增键追加到 `Settings` 末尾；不重置用户设置。
- 不修改服务端数据；所有写操作在 M2 之后单独验证。

## 14. 需要你准备/确认

1. **安装 VS 2026 + UWP 工具 + Windows SDK 10.0.26100**。这是 M0 的前置条件，当前机器没有。
2. 确认只在 **x64 Windows 11** 上自用；不做 ARM64。
3. 确认接受**登录弹窗改版**（只保留二维码，删除密码/验证码/网页迷你登录）。
4. 如果希望 1080P+/4K，需要登录有相应权益的账号；登录只解决鉴权，不改变会员权益。
5. 后台动态通知是否还需要？不需要的话 M3 直接移除，减少一个 WinRT 组件风险。
